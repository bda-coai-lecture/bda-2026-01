Slack 스레드 1개 = Claude Code 세션 1개

수강생이 Slack에 데이터 질문을 던지면, 스레드마다 독립된 분석 세션이 붙어 BigQuery를 읽고 검증된 형식으로 답한다. 이 문서는 그 구조와, 실측으로 확인한 신뢰 경계를 정리한 설계 기록이다.

Overview

요청 하나가 흐르는 경로
1 · 접수
Slack Socket Mode 멘션 또는 스레드 답글 수신. 스레드 키 = (channel, thread_ts). 핸들러는 즉시 ack하고 작업은 워커로 넘긴다 — 미응답 이벤트는 Slack이 재전송하므로 중복 세션이 생긴다.
2 · 세션 결정
결정론적 세션 ID uuid5(NAMESPACE_URL, "slack://team/channel/thread_ts"). 봇을 재시작해도 같은 스레드가 같은 세션으로 되돌아온다.
3 · 실행
턴 1은 생성, 턴 2부터는 재개 --session-id는 생성 전용이고 재사용하면 already in use로 죽는다. 이후 턴은 --resume. cwd는 매번 고정한다.
4 · 분석
analysis 스킬 모드 분류 → 인풋 9종 → 가장 싼 소스 선택 → 1일/7일 건강성 검증 → dry run → 본 분석.
5 · 응답
진행 추적 + 최종 답변 placeholder 메시지를 chat.update로 갱신(1.5초 스로틀)하고, 최종 답변은 별도 게시. 2,800자 단위로 줄 경계에서 분할.

왜 스레드마다 세션인가

분석은 한 번에 끝나지 않는다. "그럼 봇 제외하면?" 같은 후속 질문이 앞선 검증과 정의를 그대로 물려받아야 한다. 스레드는 사람이 이미 대화 단위로 쓰고 있으므로, 세션 경계를 스레드에 맞추면 별도 상태 관리가 필요 없다.

Concurrency

직렬화가 선택이 아닌 이유
같은 세션에 동시 실행하면 에러 없이 조용히 갈라진다 같은 세션 ID로 --resume을 둘 동시에 띄우면 둘 다 exit 0으로 성공하고, transcript가 분기되며 한쪽 턴이 유실된다. 다음 --resume은 한쪽 가지만 본다. Slack Bolt 기본값이 concurrency=10이라 방치하면 반드시 발생한다.

그래서 스레드 키별 락을 둔다. 다만 threading.Lock은 FIFO가 아니라서 같은 스레드에 연속으로 들어온 두 질문의 응답 순서가 뒤집힐 수 있다. 턴이 수 분씩 걸리는 작업이므로 실제로 도달 가능한 경로다 — 스레드별 큐 + 전용 소비자 스레드로 바꿔야 한다. (미해결)

항목현재상태
스레드별 상호배제키별 threading.Lock적용
중복 이벤트 제거event_id/client_msg_id, 2000건 상한적용
자기 메시지 무시bot_id + subtype + 자기 user_id적용
응답 순서 보장없음 (Lock은 FIFO 아님)미해결
동시 세션 수 상한없음 — 질문 N개 = 지출 N배미해결
재시작 후 스레드 소유권메모리에만 존재 → 재시작 시 유실미해결

Trust boundary

아무나 실행할 수 있으므로, 막는 층을 셋으로 나눈다

봇은 워크스페이스 누구나 트리거할 수 있고 답변은 Slack에 그대로 게시된다. 즉 세션이 읽을 수 있는 모든 것은 사실상 공개된다. 도구 권한만으로는 부족하다는 것을 실측으로 확인했으므로 경계를 3층으로 세운다.

1
컨테이너 — 무엇이 존재하는가

프로젝트와 read-only BigQuery 키만 마운트한다. 호스트 홈은 없다. 세션이 절대경로를 훑어도 ~/.ssh, ~/.aws, ~/.claude.json, 운영자 키가 애초에 파일시스템에 없다. 이것이 유일한 진짜 격리 경계다.

2
IAM — 데이터에 무엇을 할 수 있는가

전용 서비스 계정에 bigquery.jobUser + mart 데이터셋 dataViewer만 부여한다. dataEditor는 주지 않는다. bq query는 DDL/DML을 실행하고 명령 문자열 매칭으로 SQL을 통제할 방법이 없으므로, 읽기 전용은 IAM에서만 강제된다.

3
도구 권한 — 무엇을 시도할 수 있는가

--permission-mode manual + 허용목록 + 금지목록. 위 두 층이 실패했을 때의 방어선이자, 실수를 permission_denials[]로 가시화하는 장치다. 단독으로는 신뢰하지 않는다.

실측으로 확인한 것

추측이 아니라 실제로 실행해서 확인한 결과다. 권한 목록을 넓히기 전에 다시 측정할 것.

시도결과의미
--allowedTools 위반 도구를 auto 모드에서 실행 허용됨 거부가 기록된 뒤 재시도가 자동 승인된다. 허용목록은 manual에서만 구속력이 있다.
--disallowedTools 위반을 auto 모드에서 실행 차단됨 금지목록은 모든 모드에서 하드 거부다.
uv run python -c "open('gcp-key.json').read()" 허용됐음 → 지금은 차단 deny는 Bash 명령 문자열을 본다. 인터프리터 한 번이면 모든 deny가 무력화된다. uv run dbt만 허용으로 축소.
echo hi; touch pwn / $(...) 차단됨 매처가 ;/&&/|를 분해하고 정적 분석 불가한 치환을 거부한다. 방어 불필요.
Read로 /etc/hosts 읽기 막을 수 없음 Read(/etc/**), Read(//etc/**), Read(**/hosts), Read(/etc/*) 네 형태 모두 실패. 읽기 전용 도구는 기본 허용이라 allowlist로도 좁혀지지 않는다.
--tools로 Read/Grep/Glob 제거 후 cat /etc/hosts 차단됨 Bash는 cwd 밖 읽기를 기본 거부한다. 파일 접근을 Bash로 내리면 통제권에 들어온다.
컨테이너로 옮기면 3번 항목이 무의미해진다 호스트 홈이 없으므로 Read가 절대경로를 읽어도 볼 것이 없다. 컨테이너 실행 시에는 Read/Grep/Glob을 되돌려도 안전하다 (SESSION_TOOLS 상수 한 줄).

여전히 못 막는 것

  • bq query의 DDL/DML. 명령 문자열로 SQL을 통제할 수 없다. IAM으로만 해결된다.
  • 스캔 비용. --max-budget-usd는 Claude 지출만 막는다. BigQuery는 BIGQUERY_MAXIMUM_BYTES_BILLED(쿼리당 기본 200 GiB)로 별도 상한을 건다. 스킬의 "raw를 함부로 스캔하지 않는다"는 규칙은 산문이지 강제가 아니다.
  • 프롬프트 인젝션. Slack 원문이 프롬프트에 들어간다. 위 3층이 피해 범위를 제한하는 방식으로 대응한다.

Analysis contract

숫자보다 데이터를 먼저 의심하는 절차

외부에서 받아온 오픈 데이터셋 워크플로우를 우리 환경에 맞게 재판정한 결과다. 원문은 "구조를 모르는 데이터셋을 처음 연다"를 전제하지만 우리는 반대다 — 구조를 dbt로 이미 소유하고 있고, 대신 원천이 크고 과금된다.

원문판정이유
AB 테스트 모드삭제GH Archive에 variant 배정이 없다. 흉내내면 원문이 금지한 "해시로 임의 배정"을 하게 된다.
퍼널 모드개명fact가 payload를 버려 제품 퍼널 단계가 없다. 있는 건 에피소드 생존 단계 → 라이프사이클 단계 분석.
"결측/중복이 좀 있으면 좋다"교체fact는 not_null 테스트로 막혀 있어 null 검증이 항상 PASS. 진짜 위험은 좌·우측 절단과 자동화 actor 혼입.
가드레일 = 에러율/환불률교체우리 가드레일은 스캔 바이트와 shard 완결성. 인풋 7종 → 9종.
"데이터 구조를 읽는다"순서 교체매번 읽으면 raw로 직행한다. lineage에서 선택하는 단계로.

인풋 9종

모르는 항목은 미확인, 데이터에 없는 항목은 계측 공백. 비워둘 수 없고, 각 항목에 근거를 붙인다. 근거 없는 "확인됨"은 반증 불가능한 주장이다.

1 분석 대상        2 분석 단위(grain)   3 기간(검증/본분석)
4 기준 시간        5 대상 조건·세그먼트  6 제외 조건 ← automation_actor 필수
7 핵심 지표 1개    8 가드레일 지표       9 스캔 예산

7번은 쿼리 실행 전에 선언하고 이후 바꾸지 않는다. 8번(분석적 반대 지표)과 9번(비용 상한)은 서로 다른 것이다.

계측 공백은 "없다"로 끝내지 않는다

fact에 없어도 raw에는 대개 있다. 대신 돈이 든다. 그래서 정답 형식은 "fact에는 없음 / raw에서 N GB 스캔하면 가능"이다.

Data traps

설계에 반영된, 실재하는 함정

리텐션 계열 mart가 정의가 다른 채로 5개 공존한다

이름이 닮았고, 다섯 다 값이 나오고, 다섯 다 cohort 또는 retention이라는 단어를 쓴다. 잘못 집으면 조용히 틀린다.

모델실제 의미
metrics_retention_weekly최초 관측 코호트 — "신규 유저 리텐션"이 맞음
metrics_cohort_retention_weekly_heatmap활동주 롤링 코호트 — 신규가 아님
metrics_retention_summary최초 관측 코호트의 W0~W3 요약
metrics_user_lifecycle_weekly직전 기간 라이프사이클 회계
metrics_user_retention_weekly위 모델의 select * 별칭 — 쓰지 말 것
같은 주, 같은 "W1 리텐션", 2배 차이 2026-03-02 코호트: 최초 관측 기준 23.8%(분모 520,770) vs 활동주 롤링 기준 45.6%(분모 2,625,588). 그래서 규칙은 "이름이 겹치는 모델이 둘 이상이면 SQL을 열어 정의를 확인하기 전에 숫자를 인용하지 않는다"다.

actor의 0.27%가 event의 15.94%를 만든다

2026-07-01~07-07 PushEvent 기준. dim_push_automation_actor가 존재하는데도 fct_push_repo_episode와 metrics_daily는 이들을 제외하지 않는다. 즉 제외 여부가 모델마다 다르므로 분석마다 선택해야 하는 입력이다. 인풋 6번을 비워둘 수 없게 만든 이유다.

actor 기준 지표는 거의 안 흔들리고 event 기준 지표는 6분의 1이 날아간다. 둘을 나눠 보고한다.

mart 커버리지 ≠ fact 커버리지

metrics_daily는 2025-09-01부터, fact는 2025-05-01부터다. 2025-06-15를 조회하면 mart는 0행, fact는 1,148,747행이다. 백필 경계이지 버그가 아니다 — 그래서 정상 운영 중에도 상시 존재한다. "mart 0행 = 데이터 없음"이라는 추론은 앞으로도 계속 틀린다. 건강성 검증표에 mart 커버리지 항목을 신설한 이유다.

as-of 없는 이탈률은 무효

fct_push_repo_episode의 data_through_date는 2026-07-18로 fact보다 7일 뒤처져 있다. 에피소드의 9.65%는 아직 이탈 판정이 불가한 is_provisional이고, 93.51%는 생애 기여자가 1명뿐이다. 같은 쿼리를 일주일 뒤에 돌리면 이탈률이 바뀐다.

Slack 앱을 새로 만드는 이유 기존 "Airflow Alerts" 앱은 chat:write만 가지고 있어 이벤트를 받을 수 없다. 스코프를 추가하려면 재설치가 필요하고, 그 과정에서 xoxb 토큰이 회전하면 Airflow 알림이 조용히 멎는다 — slack_alert._post()가 실패를 삼키기 때문에 티도 안 난다. 그래서 봇 전용 앱을 따로 만든다.

Socket Mode에는 xapp- 앱 레벨 토큰이 필요하다. xoxb-로는 apps.connections.open이 not_allowed_token_type으로 거부되므로, 스코프를 아무리 추가해도 대체되지 않는다.

Open items

알고 남긴 것
  • 응답 순서 — 같은 스레드 연속 질문이 뒤집힐 수 있다. 스레드별 큐로 교체 필요.
  • 동시 세션 상한 — 없다. 질문 N개 = 지출 N배. 워커 풀 도입 필요.
  • 재시작 후 스레드 소유권 — 메모리에만 있어 멘션 없는 후속 질문이 무시된다. transcript 존재 여부로 판정하도록 변경 필요.
  • 실연결 미검증 — Bolt 핸들러, chat.update 스로틀, 청킹은 문서 스펙대로 작성했으나 실제 워크스페이스에서 돌린 적이 없다.
  • actor 급감 — 최근 2주 actor·repo가 급감하는데 event는 평평하다(event/actor 6.27 → 12.16). 드리프트 알림이 이걸 정확히 가리키고 있다. 별도 진단 진행 중.
