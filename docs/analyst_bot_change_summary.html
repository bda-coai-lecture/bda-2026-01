Slack 분석 봇 변경 요약

이번 변경은 자동화 분석 봇을 실제 Slack 운영 화면에 올릴 때 무엇을 보여주고 무엇을 기록으로 남겨야 하는지 다룬다. 핵심은 답변을 짧게 줄이는 일이 아니라, 사용자가 보는 화면과 분석자가 검증하는 기록을 분리하는 운영 계약을 만드는 것이다. 탭을 따라가면 문제 정의, 답변 변화, 구현 위치, 실행 방법, 남은 검증을 순서대로 볼 수 있다.

한 장 요약

분석 자동화는 답변 화면과 검증 기록을 분리하는 일이다

이번 변경의 중심은 Slack을 보는 사람이 제품 의사결정을 하는 사람이라는 점을 전제로, 바로 판단에 필요한 답만 보이게 만드는 것이다. 봇 러너가 중간에서 세션 순서를 잡고, 실행 근거는 기록으로 보내며, 마지막 답변만 Slack에서 읽기 좋은 형태로 다시 다듬는다.

수업 끝나고 남길 문장

분석 자동화의 품질은 모델이 SQL을 만들 수 있는지보다, 질문자용 답변과 재현 가능한 근거를 서로 다른 위치에 안정적으로 남길 수 있는지에서 갈린다.

학습 목표

문제 정의
운영 화면과 분석 기록이 섞일 때 생기는 문제를 설명한다

맞는 답이어도 Slack에서 기술 문서처럼 보이면 질문자는 결론보다 과정을 먼저 읽게 된다.

설계 판단
Slack 스레드, 분석 세션, 실행 기록의 경계를 구분한다

후속 질문의 맥락, 중단, 진행 표시, 재현 기록은 모두 같은 경계 설계에서 나온다.

검증 읽기
테스트 통과와 운영 준비 완료를 구분한다

자동 회귀, 실제 Slack 실행, 비용 상한, Metabase 연결은 서로 다른 증거다.

왜 바꿨나

문제 1
Slack 답변이 분석 기록처럼 보였다
핵심 판단

질문자는 재현 절차보다 결론, 숫자, 기준일, 한계를 먼저 봐야 한다.

바뀐 형태
  • 검증, 재현 SQL, 비용 상세는 실행 기록으로 보낸다.
  • Slack 최종 답변은 결론과 한계 중심으로 다시 정리한다.
  • 긴 분석 메모를 그대로 게시하지 않도록 후처리 관문을 둔다.
문제 2
후속 질문과 긴 실행이 꼬일 수 있었다
핵심 판단

Slack 스레드 하나가 분석 세션 하나여야 이전 정의와 필터가 이어진다.

바뀐 형태
  • 같은 스레드의 질문은 같은 Claude 분석 세션으로 이어진다.
  • 스레드별 FIFO queue로 답변 순서가 뒤섞이지 않게 했다.
  • 진행 메시지와 중단 버튼으로 오래 걸리는 실행을 운영 가능하게 했다.
문제 3
실행 환경이 사람마다 달라질 수 있었다
핵심 판단

수업, 데모, 검증 환경이 달라도 같은 명령으로 실행되게 만들 필요가 있었다.

바뀐 형태
  • Python, gcloud, dbt, BigQuery CLI가 들어간 실행 환경을 이미지로 고정한다.
  • 컨테이너 안에서 로그인, 설정 점검, 자체 점검, Slack 연결을 같은 순서로 확인한다.
  • 필요한 파일만 마운트해 개인 환경 차이와 불필요한 파일 노출을 같이 줄인다.
문제 4
테스트 통과와 운영 준비가 같은 말로 보일 수 있었다
핵심 판단

자동 테스트, 실제 Slack 실행, 비용 상한, 선택 도구 연결은 서로 다른 검증이다.

바뀐 형태
  • 검증 상태를 완료와 남은 확인으로 나눠 표시했다.
  • 실제 Slack 표현 재확인과 BigQuery hard quota는 완료로 바꾸고, Metabase 카드는 남은 항목으로 둔다.
  • 5번 탭에서 각 검증이 무엇을 증명했는지 다시 나눈다.
먼저 보는 용어 풀이

아래 용어는 문서 안에서 반복해서 나온다. 개발자가 아니어도 흐름을 따라갈 수 있게 쉬운 뜻을 같이 둔다.

제품 의사결정자기능이나 지표를 보고 다음 행동을 정해야 하는 사람. 이 문서에서는 Slack 답변의 주 독자다.
분석 세션Slack 스레드 하나에 붙는 이어지는 분석 대화. 같은 스레드 질문은 같은 흐름에서 이어진다.
실행 기록Slack에는 숨기는 자세한 근거 파일. 검증, 재현 SQL, 도구 실행 원문이 여기에 남는다.
audit/trace나중에 재현하거나 장애를 확인할 수 있게 남기는 실행 증거. Slack 답변보다 자세하다.
dbtSQL을 정리하고 검사해서 실제 조회 가능한 형태로 만드는 도구.
BigQueryGitHub Archive 데이터를 실제로 조회하는 데이터 저장소.
Metabase쿼리 결과를 카드나 대시보드 화면으로 볼 수 있게 해주는 도구.
MCPClaude가 Metabase 같은 외부 도구를 사용할 수 있게 붙이는 연결 방식.
실행 전 점검큰 쿼리를 돌리기 전에 비용과 범위를 먼저 확인하는 단계. 명령 이름은 --dry-run이다.
raw/mart/grain 등데이터가 어디에 어떤 단위로 저장됐는지 말하는 내부 구조 용어. Slack 첫 답변에는 보통 필요 없다.
기준 시간데이터 날짜를 어느 시간대 기준으로 자르는지에 대한 약속. 쉽게 말하더라도 숨기면 안 된다.
Socket Mode봇이 Slack 쪽으로 먼저 연결을 열어 메시지를 받는 방식. 공개 서버 주소 없이도 실행할 수 있다.
OAuth 로그인컨테이너 안에서 Claude 계정 사용 권한을 한 번 받아 저장하는 절차.
서비스 계정사람 계정 대신 봇이 BigQuery를 읽을 때 쓰는 낮은 권한의 계정.
FIFO queue먼저 들어온 질문을 먼저 처리하는 대기열. 같은 Slack 스레드의 답변 순서가 꼬이지 않게 한다.
Docker 마운트호스트의 특정 파일이나 폴더만 컨테이너 안에 보여주는 설정.
백그라운드 실행터미널을 계속 붙잡지 않고도 Slack 연결이 유지되게 띄우는 방식.
문서 흐름

1번 탭은 전체 지도, 2번 탭은 실제 Slack 답변이 어떻게 바뀌었는지, 3번 탭은 코드에서 무엇을 고쳤는지, 4번 탭은 Docker 안에서 어떻게 띄우는지, 5번 탭은 검증 상태와 이 사례에서 가져갈 교훈을 보여준다.

변경을 한 문장으로

분석 과정은 더 엄격하게 남기되, Slack에는 질문자가 바로 판단할 수 있는 답변만 보이게 했다. 그래서 정확성 확인과 사용자 경험을 같은 메시지에 우겨 넣지 않는다.

이 작업은 답변을 대충 줄인 것이 아니다. Slack 사용자가 보는 화면과 개발자가 나중에 확인하는 실행 기록을 분리한 것이다. 그래서 답변은 쉬워졌지만, 검증과 재현 가능성은 실행 기록 쪽에 더 분명하게 남는다.

답변 흐름

외부의 좋은 사용 사례에서 운영 패턴을 가져왔다

이번 작업은 외부 Slack 분석 봇 사례의 구현을 통째로 복사한 것이 아니라, 그 사례에서 검증된 운영 습관을 현재 봇에 맞게 번역한 것이다. 질문을 받으면 기다리는 사람에게 진행 상황을 보여주고, 답변은 바로 읽히게 만들고, 자세한 근거는 나중에 확인할 수 있게 따로 남기는 방식이다.

여기서 가져온 패턴

가져온 것은 코드가 아니라 아래 5단계 운영 흐름이다. Slack 질문을 하나의 분석 턴으로 잡고, 기다리는 사람에게 진행 상태를 보여주며, 분석 실행은 내부에서 처리하고, 게시 직전에는 Slack용 답변만 남기는 흐름이다. 이 5단계가 외부 사례에서 배운 부분이고, 구현 세부보다 운영 습관을 현재 봇에 맞게 옮겼다는 점이 핵심이다.

01
Slack 질문

멘션이나 DM으로 들어온 질문을 하나의 분석 턴으로 잡는다.

02
진행 메시지

복잡한 로그 대신 사람이 읽는 상태와 중단 버튼을 보여준다.

03
분석 실행

Claude, dbt, BigQuery를 쓰되 내부 경로와 비용 상세는 숨긴다.

04
답변 정리

게시 직전에 기술 메모, 재현 경로, 토큰 패턴을 걷어낸다.

05
Slack 최종 답변

결론, 핵심 숫자, 기준일/기간, 한계만 남긴다.

협업 메모

외부 사례에서 가져온 것은 위 5단계 운영 흐름이다. 반대로 active actor를 활동 계정처럼 바꾸고, 짧은 질문에는 짧게 답하게 만든 일은 오늘 실제 Slack 답변을 보면서 같이 조정한 결과다. 작업 중 계속 잡았던 기준은 “분석자용 근거는 실행 기록, Slack은 의사결정 화면”이었다.

오늘 작업은 결과를 보면서 계속 고친 루프였다

1

전체 운영 흐름을 먼저 붙였다

본 사례외부의 좋은 Slack 분석 봇은 진행 상태, 중단, 답변, 실행 기록이 한 흐름으로 묶여 있었다.
판단지금 봇도 “질문을 받았다”에서 “근거를 남겼다”까지 한 번에 이어져야 한다.
수정스레드별 세션, 진행 메시지, 중단 버튼, 피드백, 실행 기록 저장을 먼저 붙였다.
2

실제 테스트 질문

Docker로 띄운 뒤 Slack에서 “최근 완료된 1일 active actor 수 간단히 봐줘”라고 물었다. 기능은 성공했다. 봇은 Slack 이벤트를 받고, BigQuery를 조회하고, 답변까지 게시했다. 하지만 답변이 active actor, actor.id, UTC, 토요일 비교표까지 포함해 “간단히”라는 요청에 비해 너무 기술적으로 읽혔다. 아래 오른쪽은 그 관찰을 바탕으로 다시 잡은 교육용 목표 형태다.

Slack UX

이 부분은 실제 답변을 보면서 피드백 왕복으로 나온 변경이다

외부 사례에서 가져온 것은 운영 흐름이고, 아래 용어 조정은 오늘 실제 Slack 답변을 보면서 만든 것이다. active actor, actor.id, distinct count 같은 말이 앞에 나오면 제품 의사결정자 입장에서는 답보다 데이터 모델 설명을 먼저 읽게 된다. 그래서 지표명은 유지하되, 첫 표현은 질문자가 바로 이해할 수 있는 말로 바꾸고, 원래 스키마 기준이 꼭 필요하면 한계 문장이나 괄호 안에서 보충한다.

mart/raw/shard/partition/grain 필요하면 풀어서 설명 내부 구조는 답변의 주인공이 아니게 한다.

Docker

Docker는 어디서나 같은 방식으로 실행하기 위해 넣었다

여기서 Docker는 회사 프로덕션 배포처를 뜻하지 않는다. 실제 회사라면 개인 노트북이 아니라 서버, 컨테이너 플랫폼, 예약 잡 같은 운영 런타임에 올리고 Secret Manager, IAM, 모니터링을 붙인다. 이 문서의 Docker는 수업, 데모, 검증 환경이 바뀌어도 같은 명령과 같은 의존성으로 봇을 띄우기 위한 실행 패키징이다.

그래서 핵심은 Python, gcloud, dbt, BigQuery CLI, Claude 로그인 저장 위치, 로그 저장 위치를 매번 같은 형태로 맞추는 것이다. 동시에 필요한 경로만 마운트하면 개인 컴퓨터의 임의 파일을 컨테이너 안으로 끌고 들어오지 않아도 되므로, 파일 노출 범위도 함께 깔끔해진다.

Docker 운영 원문에서 가져온 판단

핵심은 “환경을 이미지로 고정하고, 마운트는 필요한 만큼만 둔다”이다. 실행 환경을 고정해야 다른 컴퓨터에서도 같은 방식으로 검증할 수 있고, 마운트를 좁혀야 개인 설정이나 키 파일이 우연히 컨테이너 안에 들어오지 않는다. 아래 구조도와 실행 순서는 이 두 목적을 함께 보여준다.

호스트 로그인을 그대로 넘기지 않는다. 컨테이너 안에서 한 번 Claude 계정 로그인을 하고, 결과는 analyst-claude라는 Docker 저장 공간에 저장한다. 이후에는 컨테이너를 껐다 켜도 같은 로그인을 재사용한다.

실행 순서

1. 이미지 만들기

컨테이너 안에서 필요한 Python, gcloud, dbt, BigQuery CLI가 같이 들어간 실행 환경을 만든다.

docker compose build analyst-bot

2. 컨테이너 안에서 로그인

호스트 로그인 파일을 넘기지 않고, 봇 컨테이너가 직접 Claude 로그인을 갖게 한다.

docker compose run --rm -it --entrypoint claude analyst-bot auth login

3. 실행 전 점검

실제 Slack을 처리하기 전에 필요한 파일, 로그 저장 위치, 쿼리 기본 상한이 잡혔는지 확인한다.

docker compose run --rm analyst-bot --dry-run

4. 백그라운드로 켜기

터미널을 닫아도 Slack 이벤트를 계속 받을 수 있게 띄우고, 로그로 상태를 본다.

docker compose up -d analyst-bot
docker compose logs -f analyst-bot

실습 체크 기준

확인할 것 성공으로 보는 신호 막히면 먼저 볼 곳
이미지 빌드 Python, gcloud, dbt, BigQuery CLI가 들어간 이미지가 끝까지 만들어진다. Dockerfile과 entrypoint에서 설치 단계가 실패했는지 본다.
컨테이너 로그인 컨테이너 재시작 뒤에도 Claude 로그인이 유지된다. 호스트 로그인 파일을 넘기려 하지 말고 Docker 저장 공간이 유지되는지 본다.
실행 전 점검 레포 위치, 실행 기록 저장 위치, BigQuery 계정, 기본 스캔 상한이 출력된다. 마운트 경로, BigQuery 키, .bigqueryrc 적용 여부를 본다.
세션 이어가기 첫 질문과 후속 질문이 같은 Slack 스레드 세션으로 이어진다. 스레드 키와 session id 생성 규칙, --resume 경로를 본다.
백그라운드 실행 로그에 Slack 연결 완료 문구가 보이고, 터미널을 닫아도 봇이 유지된다. Slack 앱 설정, 토큰 환경변수, 허용 채널, 컨테이너 로그를 차례로 본다.
실습에서 헷갈리기 쉬운 점

--dry-run은 실제 Slack 질문을 처리했다는 뜻이 아니다. 설정과 실행 경로가 잡혔는지 보는 단계다. 실제 운영 표면은 Slack에서 짧은 질문을 던지고, 답변 표현과 실행 기록 저장을 함께 확인해야 한다.

이 사례에서 배울 것

원칙 1
사용자 화면은 의사결정용으로 설계한다

결론, 숫자, 기준일, 한계를 먼저 보이고 재현 경로는 실행 기록으로 보낸다.

원칙 2
검증 가능성을 없애지 않고 위치를 바꾼다

Slack에서 지운 정보가 사라진 것이 아니라 audit/trace에 남아야 운영 가능한 자동화다.

원칙 3
실행 환경은 말이 아니라 이미지와 명령으로 고정한다

의존성과 실행 순서를 컨테이너로 묶고, 마운트와 낮은 권한 계정으로 불필요한 노출을 줄인다.

원칙 4
테스트 통과와 운영 준비 완료를 구분한다

자동 테스트, 실제 Slack 실행, 비용 상한, 선택 도구 연결은 각각 따로 확인해야 한다.

포트폴리오 문장으로 번역

Slack 기반 분석 자동화 봇에서 최종 답변 후처리, 스레드별 세션 관리, 실행 기록 분리, Docker 실행 환경, 제한된 마운트, 비용 상한 점검을 설계해 분석 결과의 사용자 경험과 재현 가능성을 분리했다.
