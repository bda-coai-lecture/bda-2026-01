BDA 2 · Analyst Bot Lecture
2026-08-09 · Slack automation audit

분석 자동화 봇은 답변보다 로그가 더 중요하다

Slack에서 질문을 받는 봇은 “한 번 답을 잘했다”로 끝나지 않는다. 질문, 도구 사용, 비용, 실패, 피드백이 테이블로 남아야 나중에 채점하고, 반복 실패를 찾고, 프롬프트와 데이터 모델을 개선할 수 있다. 이 문서는 별도 RDS/Postgres audit 테이블을 중심으로 봇의 데이터 흐름과 피드백 루프를 설명한다.

Thesis

분석 봇의 핵심 산출물은 Slack 답변 하나가 아니라, 다시 학습 가능한 실행 기록이다.

Primary Surface
Slack thread
사용자는 질문과 최종 답만 본다.
Durable State
RDS/Postgres + JSONL
채점, 장애 조사, 비용 추적은 테이블에서 한다.
Feedback Unit
audit_id
질문, 답변, trace, 비용, 버튼 피드백을 묶는 키다.
Improvement Target
workflow, prompt, mart
틀린 답만 고치는 것이 아니라 반복 실패 경로를 고친다.
강의 메시지

LLM 분석 자동화에서 “결과를 저장한다”는 말은 답변 텍스트를 보관한다는 뜻이 아니다. 어떤 질문이 들어왔고, 어떤 세션 문맥으로 실행됐고, 어떤 데이터 소스를 조회했고, 비용 제한과 권한 제한을 어떻게 통과했는지까지 남겨야 재현 가능한 시스템이 된다.

Before
JSONL만 있으면 운영 증거는 있지만 비교 분석이 불편하다.

파일을 직접 뒤져야 하므로 “최근 부정확 피드백이 늘었나?”, “BigQuery 비용이 큰 질문 유형은?” 같은 질문이 느리다.

After
별도 Postgres에 넣으면 봇 자체도 분석 대상이 된다.

질문-답변-사용량-피드백을 SQL로 묶어서 보고, Metabase 카드나 평가 리포트로 확장할 수 있다.

Principle
사용자용 답변과 운영용 증거는 분리한다.

Slack에는 짧고 읽기 쉬운 답만 남기고, dry-run bytes, tool trace, permission denial은 audit 테이블로 보낸다.

좋은 로그의 조건

조건봇에서의 의미나중에 가능한 일
구조화 `status`, `bq_gib`, `permission_denials`, `feedback_type`처럼 컬럼으로 저장한다. 실패율, 비용, 피드백을 SQL로 바로 집계한다.
연결성 `audit_id`로 turns, usage, trace, feedback, eval score를 묶는다. 특정 답변이 왜 틀렸는지 실행 경로까지 내려간다.
비밀 분리 Audit DB URL은 봇 프로세스만 읽고 Claude child env에서는 제거한다. 분석 세션이 audit DB credential을 볼 수 없다.
실패 격리 Postgres 쓰기가 실패해도 JSONL은 남고 Slack 답변은 계속 간다. 관측 시스템 장애가 사용자 경험을 망치지 않는다.

Data Flow

하나의 Slack 질문은 세 가지 산출물을 만든다: 사용자 답변, 실행 증거, 개선 데이터.

Slack 질문
멘션 또는 DM. thread key는 `(team, channel, thread_ts)`다.
→session id
Claude session
thread key에서 결정론적 `session_id`를 만들고 `--resume`으로 문맥을 이어간다.
→tool trace
BigQuery / dbt
작은 범위 검증, dry-run, mart 우선, raw는 `_TABLE_SUFFIX`로 제한한다.
→answer + audit
RDS/Postgres audit
질문, 답변, 비용, trace, 피드백을 테이블로 저장한다.
Slack-visible lane

사용자는 진행 메시지와 최종 답변만 본다. 최종 답변에는 실행 시간과 “상세 실행 내역은 로그에 저장됨” 정도만 붙는다. Claude 턴 수, BigQuery GiB, dry-run 바이트, tool 이름은 숨긴다.

Audit lane

같은 턴에서 `turns`, `turn_usage`, `trace_events`, `feedback`이 채워진다. Slack 답변은 제품 표면이고, audit 테이블은 운영 표면이다. 둘을 분리해야 답변은 읽기 쉽고 운영자는 충분한 증거를 갖는다.

Fallback lane

JSONL은 계속 저장한다. Postgres 연결이 끊기거나 테이블 권한이 틀려도 로컬 로그는 남기고, 나중에 `scripts/backfill_analyst_audit_to_postgres.py`로 재적재한다.

턴 하나에서 발생하는 이벤트

순서이벤트저장되는 위치사용자에게 보이는가
1Slack 메시지 수신, `audit_id` 생성`threads`, `turns` 준비아직 안 보임
2Claude session 실행`trace_events` 후보 line 수집진행 메시지만 보임
3BigQuery 사용량 집계`turn_usage.bq_*`세부값은 숨김
4최종 답변 정리`turns.answer`Slack 최종 답변
5버튼 피드백 클릭`feedback`피드백 기록 상태만 보임
설계 포인트

trace는 turn row 뒤에 저장한다. `trace_events.audit_id`가 `turns.audit_id`를 참조하기 때문이다. 순서를 바꾸지 않으면 Postgres에서는 FK 오류가 난다.

Schema

테이블은 “대화”, “실행”, “사용량”, “피드백”, “채점”을 분리한다.

테이블grain핵심 컬럼왜 분리하나
threads Slack thread 1개 `team_id`, `channel_id`, `thread_ts`, `session_id` 같은 스레드의 후속 질문을 같은 Claude session으로 묶는다.
turns 분석 요청 1회 `audit_id`, `question`, `answer`, `status`, `error` 사용자가 체감한 요청 단위다. 채점과 피드백의 중심 키다.
turn_usage 분석 요청 1회 `claude_turns`, `bq_billed_bytes`, `bq_gib`, `permission_denials` 비용과 권한 문제는 답변 품질과 다른 축이라 별도 관리한다.
trace_events compact trace line `event_type`, `text`, `payload`, `seq` 답변이 틀렸을 때 “어느 단계에서 틀렸나”를 재구성한다.
feedback 피드백 클릭 1회 `feedback_type`, `user_id`, `created_at` 사람이 느낀 품질 신호를 턴에 연결한다.
eval_cases 계열 채점 문제와 실행 `rubric_version`, `expected`, `score`, `details` 수동 피드백을 정량 평가 루프로 확장한다.

Operational table

운영자가 지금 보는 질문

  • 최근 실패한 요청은 무엇인가?
  • Slack에는 성공처럼 보였지만 delivery가 실패한 턴이 있는가?
  • BigQuery 사용량 집계가 깨졌는가?
  • 권한 deny가 잦은 도구는 무엇인가?

Evaluation table

개선 담당자가 나중에 보는 질문

  • 어떤 질문 유형에서 답변이 길어지는가?
  • 틀린 답변은 lineage 확인을 건너뛰었는가?
  • 피드백이 나쁜 답변은 비용도 높은가?
  • rubric version을 바꾼 뒤 품질이 올랐는가?

채점용 view

`v_turns_for_scoring`은 한 줄에 질문, 답변, 비용, 피드백을 모아준다. evaluator나 Metabase 카드는 이 view부터 보면 된다. 

select
  audit_id,
  status,
  started_at,
  question,
  answer,
  bq_gib,
  bq_error,
  feedback
from analyst_audit.v_turns_for_scoring
order by started_at desc
limit 20;
주의

질문과 답변 원문은 제품/운영 맥락을 포함한다. RDS DB 권한은 내부 운영자와 봇 전용 user에만 열고, anon/public key나 클라이언트 SDK로 이 테이블을 직접 노출하지 않는다.

Feedback Loop

피드백 루프는 “버튼 클릭”이 아니라, 실패 유형을 찾아 절차를 바꾸는 닫힌 회로다.

질문 수집

Slack 질문과 thread context를 `turns`에 저장한다. 실제 사용자의 언어가 testset 후보가 된다.

실행 증거 수집

도구 trace, 비용, deny, 오류를 `trace_events`와 `turn_usage`로 분리해 남긴다.

사람 피드백

답변 버튼이 `helpful`, `inaccurate`, `needs_more_investigation`으로 저장된다.

실패 분류

틀린 숫자, 너무 긴 답변, 비용 초과, lineage 누락, caveat 누락처럼 원인을 태깅한다.

절차 개선

프롬프트, analysis skill, mart, guardrail, testset 중 맞는 레이어를 바꾼 뒤 재채점한다.

피드백을 어떻게 해석할까

피드백일차 해석바로 보면 좋은 컬럼가능한 개선
helpful 사용자 목적에는 맞았다. `duration_ms`, `bq_gib`, `answer` 길이 좋은 답변 패턴을 prompt example이나 testset 기준으로 승격한다.
inaccurate 숫자, 기간, 정의, source 선택 중 하나가 틀렸을 가능성이 높다. `trace_events`, `permission_denials`, 사용 SQL path lineage 확인, raw/mart reconcile, metric definition을 testset에 추가한다.
needs_more_investigation 결론은 유용하지만 근거가 얕거나 caveat가 부족했다. `answer`, `trace_line_count`, `bq_jobs` 답변에 필요한 최소 caveat와 추가 분석 trigger를 조정한다.

품질 이슈 찾기

select
  f.feedback_type,
  count(*) as turns,
  avg(t.duration_ms) / 1000 as avg_seconds,
  avg(u.bq_gib) as avg_bq_gib
from analyst_audit.feedback f
join analyst_audit.turns t using (audit_id)
left join analyst_audit.turn_usage u using (audit_id)
group by 1
order by turns desc;

비용 큰 질문 보기

select
  t.started_at,
  t.status,
  left(t.question, 120) as question,
  u.bq_gib,
  u.bq_jobs,
  u.bq_error
from analyst_audit.turns t
join analyst_audit.turn_usage u using (audit_id)
order by u.bq_gib desc nulls last
limit 20;
강의 포인트

피드백 루프는 모델을 바로 fine-tune하는 이야기가 아니다. 대부분의 개선은 prompt, 비용 guardrail, dbt mart, health check, 답변 후처리에서 먼저 일어난다. 테이블은 어떤 레이어를 고쳐야 하는지 알려주는 증거다.

Guardrails

분석 자동화 로그에는 민감 정보와 비용 정보가 섞인다. 그래서 저장 경계가 설계의 일부다.

Credential boundary
Audit DB URL은 child env에서 제거한다.

Claude 세션은 `ANALYST_AUDIT_DATABASE_URL`을 볼 수 없다. DB write는 봇 프로세스가 담당한다.

Data boundary
JSONL은 fallback, Postgres는 질의용이다.

DB 장애가 있어도 Slack 답변은 막지 않고, 나중에 backfill로 테이블을 복구한다.

Cost boundary
Claude 환산 cost와 BigQuery 실제 스캔을 분리한다.

Claude CLI cost는 구독 사용량의 API 환산값이고, BigQuery GiB/USD가 실제 비용 축이다.

Slack boundary
Slack에는 운영 세부값을 숨긴다.

사용자 답변은 결론 중심으로 유지하고, dry-run bytes와 tool trace는 audit에만 남긴다.

실패 모드별 저장 위치

실패 모드Slack 표면테이블 표면운영 액션
Claude timeout 명시적 실패 메시지 `turns.status = error`, `turns.error` 질문 유형, trace 마지막 단계, timeout 값을 본다.
도구 권한 거부 내부 권한 문자열은 숨김 `turn_usage.permission_denials` allowlist가 너무 좁은지, 세션이 위험한 명령을 시도했는지 나눈다.
BigQuery 사용량 집계 실패 최종 답변에는 숨김 `turn_usage.bq_error` 계측용 service account와 `INFORMATION_SCHEMA.JOBS` 권한을 확인한다.
Postgres write 실패 답변은 계속 전달 JSONL에는 남고 프로세스 로그에 경고 스키마, URL, 네트워크, DB 권한 확인 후 backfill한다.
하지 말 것

RDS를 연결한다고 해서 owner key나 `.env` 전체를 컨테이너에 더 마운트하지 않는다. 이 봇의 격리 경계는 좁은 Docker mount 목록이다. 마운트를 늘리면 Read 도구 위험이 다시 커진다.

운영 체크리스트

  1. 별도 audit DB에서 `scripts/analyst_audit_schema.sql` 실행.
  2. `.env`에 `ANALYST_AUDIT_DATABASE_URL`과 `ANALYST_AUDIT_SCHEMA` 추가.
  3. `docker compose build analyst-bot`로 `psycopg` 포함 이미지 재빌드.
  4. `docker compose run --rm analyst-bot --dry-run`에서 `audit_database = configured` 확인.
  5. 짧은 Slack canary 후 `analyst_audit.v_turns_for_scoring`에서 row 확인.
마무리

이 구조를 갖추면 다음 단계는 자동 채점이다. `docs/analysis_testset.md`의 문제를 `eval_cases`에 넣고, Slack 또는 CLI로 실행한 결과를 `eval_runs`, `eval_scores`에 연결하면 봇 개선이 “느낌”이 아니라 회귀 테스트가 된다.
