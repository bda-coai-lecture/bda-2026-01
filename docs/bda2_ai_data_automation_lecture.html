AI를 통한 데이터 자동화 분석

이 강의의 출발점은 "AI가 분석을 대신한다"가 아니다. AI가 SQL과 차트 생성을 빠르게 도와주는 환경에서, 사람이 무엇을 정의하고, 어디까지 읽고, 어떻게 검증하고, 어떻게 운영할지를 배우는 것이다.

00 지난 회차와 강의 비교

BDA 1은 개념을 먼저 깔고 구현했다면, BDA 2는 결과물을 만들며 필요한 디테일을 역추적한다

  • 지난 회차는 vectorize, dict/hash처럼 성능을 좌우하는 기초 개념을 먼저 공부했다.
  • 이번 회차는 그런 지식을 하나하나 미리 다 깔고 시작하기보다, 결과물을 만들면서 필요한 디테일을 파고든다.
  • 핵심 질문은 "이 개념을 알고 구현했나"에서 "이 결과가 왜 이렇게 나왔고, 어디를 의심해야 하나"로 이동한다.

지난 회차에서 먼저 깔고 공부한 것

지난 회차

vectorize로 NumPy/Pandas 고속 연산을 이해했다

  • Python 반복문과 벡터 연산의 속도 차이를 본다.
  • row 단위 처리보다 column/batch 연산이 빠른 이유를 이해한다.
  • Pandas 코드가 느려지는 지점을 직접 고쳐본다.
지난 회차

dict와 hash로 시공간 복잡도를 익혔다

  • list scan과 dict lookup의 차이를 비교한다.
  • O(n), O(1) 같은 시간 복잡도를 실제 코드 속도로 확인한다.
  • 메모리를 더 쓰고 속도를 얻는 trade-off를 배운다.
지난 회차

자료구조가 계산 비용을 바꾼다는 감각을 익혔다

  • sparse matrix와 dense matrix의 차이를 본다.
  • join, groupby, indexing이 느려지는 이유를 확인한다.
  • 모델 입력 형태가 학습 시간과 메모리에 주는 영향을 본다.
구분지난 회차의 중심BDA 2의 중심
학습 대상 성능과 구현을 이해하기 위한 기초 개념 결과물을 만들며 드러난 문제를 파고드는 분석 운영 감각
학습 순서 개념 이해 → 코드 구현 → 결과 확인 결과물 생성 → 이상 지점 발견 → 필요한 개념 역추적
코드 디테일 미리 공부하고 나서 실습에 들어간다 먼저 만들고, 제대로 안 돌아가는 지점에서 깊게 판다
AI의 역할 보조 도구 또는 검색 도구 SQL, Python, 차트, 기본 최적화 초안을 빠르게 만드는 실행 파트너
사람의 역할 개념을 이해하고 직접 구현하는 사람 결과를 의심하고 원인을 추적하며 통제하는 설계자

이번 회차에서 보여줄 것

AI가 해주는 것사람이 확인할 것보여줄 산출물
차트 후보를 여러 개 만든다 차트가 예뻐 보여도 같은 지표 정의, grain, 기간, 분모를 쓰는지 확인한다 metric mart 기반 Metabase dashboard
SQL 초안을 빠르게 만든다 빨리 돌아가는 것처럼 보여도 _TABLE_SUFFIX, partition filter, dry run bytes를 확인한다 비용 추적, scan guard, partition 판단
반복 질문에 답변한다 답이 자연스러워 보여도 근거, 한계, 실패 로그, 비용 푸터가 남는지 확인한다 Slack 분석 봇, audit trail
코드와 최적화 방식을 제안한다 제안이 그럴듯해 보여도 결과가 이상하면 멈추고 lineage와 입력 데이터를 다시 본다 dbt test, lineage, 운영 체크리스트
결론
  • 기초 지식이 중요하지 않다는 뜻이 아니다.
  • 다만 모든 디테일을 미리 공부한 뒤 시작하는 방식은 점점 비효율적이다.
  • 먼저 만들고, 이상한 지점에서 멈추고, 그때 필요한 개념을 끝까지 파고드는 사람이 필요하다.
  • 제대로 안 돌아가는 낌새가 보이면 넘기지 말고, 원인을 의심하고 통제하는 집요한 설계자가 되어야 한다.

01 DA 인식 계보

DA의 일은 모델과 쿼리를 직접 만드는 사람에서, 질문과 지표의 책임을 지는 사람으로 이동했다

이 계보는 업계 전체를 통계적으로 대표한다기보다, 강의자가 현장에서 체감한 인식 변화에 가깝다. 중요한 것은 어느 연도에 정확히 무슨 일이 있었는지가 아니라, 도구가 쉬워질수록 DA에게 남는 책임이 무엇인지를 보는 것이다.

2017~19

ML/DL이 슬슬 알려지기 시작했다

"데이터 분석가가 머신러닝과 딥러닝도 해야 하는 것 아닌가?"라는 기대가 커졌다. 분석가의 일이 리포트와 통계에서 모델 학습까지 넓어지는 것처럼 보였다.

2020~21

제대로 쓰려면 인프라와 개발력이 필요하다는 사실이 보였다

모델 하나를 노트북에서 돌리는 것과 서비스에 붙이는 것은 달랐다. 데이터 엔지니어, ML 엔지니어, 분석가, 백엔드 개발자의 경계가 조금씩 분화됐다.

2021~22

DA는 다시 분석가 쪽으로 좁혀졌다

많은 조직에서 DA는 ML/DL 모델을 직접 만드는 사람이라기보다, SQL과 비즈니스 맥락을 바탕으로 지표를 해석하고 전략을 제안하는 역할로 인식됐다.

2023~24

GPT로 상상이 다 이루어질 것처럼 보였다

"일단 GPT로 해보라니까?"라는 분위기 속에서 빠른 프로토타입과 자동 생성 결과가 쏟아졌다. 동시에 문제 정의와 검증 없이 그럴듯하기만 한 제품, 기획, 분석도 같이 늘어났다.

2024~25

단순 쿼리 작성자로서의 DA 가치는 약해졌다

AI가 SQL 초안을 빠르게 만들기 시작하면서 "쿼리 짜는 일은 대체되는 것 아닌가"라는 질문이 커졌다. 하지만 실제로 중요한 것은 쿼리 문법보다 지표 정의, grain, 제외 조건, 해석, 액션 아이템이었다.

2025~26

모두가 무언가를 만드는 시대로 넘어갔다

AI 기반 도구 덕분에 앱, 대시보드, 봇, 분석 리포트의 첫 버전은 훨씬 쉽게 만들어졌다. 직무 경계는 흐려졌고, "만드는 능력"보다 "만든 것이 맞는지 판단하는 능력"이 더 중요해졌다.

2025~

만드는 것은 쉬워졌고, 전문가의 필요성은 아직 남아 있다

AI는 실행 속도를 올린다. 그러나 어떤 질문이 좋은 질문인지, 어떤 숫자를 믿을지, 어떤 결론을 조직의 행동으로 바꿀지는 여전히 사람이 책임져야 한다.

바뀐 오해

DA는 SQL을 치는 사람이다

SQL은 중요한 도구지만 정체성은 아니다. 같은 SQL도 지표 정의가 다르면 완전히 다른 답을 낸다.

남은 책임

무엇을 세는지 정한다

분석 대상, 관측 grain, 기준 시간, 기간, 세그먼트, 제외 조건을 고정해야 AI 결과도 검증할 수 있다.

새 역할

AI 결과의 감사자가 된다

빠른 초안은 AI에게 맡기되, lineage와 비용, 반례, 한계, 액션 아이템은 사람이 끝까지 확인한다.

비유: 지록위마형 참모

진지한 비유로는 "지록위마"가 잘 맞는다. 권력자가 듣고 싶은 답이 먼저 정해져 있고, 똑똑한 참모가 그럴듯한 문서와 근거를 만들어준다. 주변 사람들은 이상하다는 것을 알지만 분위기 때문에 침묵한다.

AI 시대의 위험도 여기에 가깝다. AI가 항상 문제라기보다, 사람이 원하는 결론을 정해두고 AI에게 근거를 만들게 할 때 분석은 더 빠르고 자신 있게 망가진다.

02 Python vs SQL

예전 질문은 Python이냐 R이냐였고, 지금 질문은 무엇을 먼저 해야 하느냐다

예전 논쟁: Python vs R

흐름

사실상 주류는 Python이 가져갔다

  • 분석, 자동화, 백엔드, ML, 데이터 파이프라인을 한 언어로 이어붙이기 쉽다.
  • 라이브러리 생태계와 커뮤니티가 넓어 문제를 만났을 때 우회로가 많다.
  • 뭐부터 공부할지 모르겠다면 Python부터 시작하는 선택이 가장 무난하다.
이유

접착성과 확장성이 컸다

  • 노트북, API, 배치 작업, 웹 서비스, 모델 학습을 한 흐름으로 묶을 수 있다.
  • 데이터 분석에서 만든 코드를 서비스나 자동화로 밀어붙이기 좋다.
  • 편의성만이 아니라 이후 확장 경로가 넓다는 점이 강했다.
예외

그래도 R이 사라진 것은 아니다

  • 통계 모델링, 계량, 실험 설계, 학술 분석 일부에서는 여전히 R을 쓴다.
  • 이미 R 기반으로 돌아가는 조직과 코드베이스도 있다.
  • 정답은 없지만, 첫 언어를 고르라면 Python이 덜 막막하다.

지금 질문은 달라졌다

먼저 물을 것
  • 공부해야 하는가 이전에, 그것을 공부하는 것이 왜 필요한가를 물어야 한다.
  • 기술 이름을 고르는 문제처럼 보이지만, 실제로는 내가 어떤 문제를 열어보고 싶은지의 문제다.
  • AI 시대에는 도구 문법보다도, 왜 그 도구가 필요한지 설명하는 능력이 더 중요해진다.
쿼리

데이터 분석가는 쿼리치는 존재인가?

  • 아니다. 쿼리는 데이터를 열어보는 도구 중 가장 유용한 것일 뿐이다.
  • 상황이 달라지면 Excel이든 Python이든 BI든 도구 자체는 바뀔 수 있다.
  • AI 시대에는 SQL 문법을 외우는 것보다, 무엇을 확인해야 하는지 아는 쪽이 더 중요해진다.
  • 다만 기술적으로 보면 쿼리 문법보다 DB를 이해하는 것이 더 중요하다.
  • 그래서 계속 OLAP/OLTP, warehouse, partition, scan cost를 이야기했다.
머신러닝

머신러닝을 공부해야 하나?

  • 글쎄. 먼저 내가 머신러닝을 잘 알아야 하는 사람인지 물어야 한다.
  • 내 방향이 ML을 이용해 서비스를 만들고 개선하는 쪽인지부터 봐야 한다.
  • ML은 너무 넓다. 어떤 기술을 배워서 어디에 쓸지 정하지 않으면 금방 흐려진다.
  • 연구가 목적이 아니라면, 공부할 기술보다 활용처를 먼저 고민하는 편이 낫다.
제품

제품을 만들어야 하나?

  • 제품을 만드는 것은 너무 좋은 경험이다.
  • 다만 내가 창업자인지, 분석가인지, 학습자인지 먼저 구분해야 한다.
  • 제품을 만들기 위해 필요한 시간과 지식은 생각보다 훨씬 많다.
  • 분석 공부의 수단으로 만들 것인지, 실제로 운영할 제품을 만들 것인지 잘 생각해봐야 한다.
