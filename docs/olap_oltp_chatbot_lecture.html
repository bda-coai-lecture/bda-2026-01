OLAP/OLTP는 챗봇의 읽기와 쓰기에서 바로 보인다

분석 자동화 챗봇은 BigQuery와 dbt mart를 읽어 답을 만들고, 방금 생긴 질문과 답변, 비용, 피드백은 Postgres/RDS audit에 남긴다. 그 기록은 다시 warehouse로 올라가 품질, 비용, 실패 패턴을 보는 데이터가 된다. 같은 구조가 ML 서비스에서는 feature, model, online serving, feedback loop로 이어진다.

Thesis

서비스 이벤트는 row로 남고, 분석 질문은 warehouse에서 풀린다.

Read Path
BigQuery + dbt mart
과거 이벤트, 지표, segment, trend를 읽음.
Write Path
Postgres / RDS audit
질문, 답변, 상태, 비용, feedback을 row로 저장.
Loop
OLTP -> OLAP
audit 기록이 CDC, batch, dbt를 거쳐 mart가 됨.
Serving
RDB / cache / online store
API 요청 path에서는 key lookup과 낮은 지연이 필요.

강의 흐름

먼저 챗봇의 read/write path를 잡고, OLTP/OLAP의 workload 차이를 본다. 다음으로 RDS CDC, event log, SaaS/API 데이터가 warehouse로 모이는 과정을 보고, scheduler와 ML serving까지 이어서 정리한다.

Concept

OLTP는 현재 상태와 작은 거래, OLAP은 누적 기록과 집계.

OLTP

서비스에서 지금 발생한 row 처리

  • insert, update, delete가 자주 일어남.
  • 동시 요청이 들어와도 상태가 안정적으로 유지되어야 함.
  • 특정 key로 빠르게 찾는 index lookup이 자주 등장.
  • 예: 질문 저장, 주문 생성, 피드백 클릭, 턴 상태 업데이트.

OLAP

많은 기록을 모아 분석 질문 처리

  • 기간, segment, 이벤트 타입별 집계가 많음.
  • 많은 row를 scan하고 aggregate하는 처리량이 중요.
  • columnar, distributed, MPP 성격의 엔진이 자주 등장.
  • 예: DAU 추세, repo segment 분석, cohort retention, 비용 리포트.

같은 SQL, 다른 목표

구분OLTPOLAP
대표 질문이 요청이 저장됐나?지난 4주 지표가 왜 움직였나?
데이터 범위몇 row, 특정 key수백만에서 수십억 row
중요 기준일관성, 동시성, 낮은 지연scan 처리량, 집계, 비용
BDA2 예시analyst_audit.turnsmetrics_daily, retention mart

제품명, query shape, SLA, grain을 같이 본다. Postgres에서도 작은 분석은 가능하고, BigQuery에도 write API가 있다. 설계할 때는 주된 사용 패턴을 먼저 확인한다.

Read lane

챗봇 질문은 GitHub Archive raw, fact_user_repo_activity, dbt metrics_* mart를 읽는다. DAU, event mix, retention, repo trend처럼 많은 row를 묶어 답하는 질문이 많다.

Write lane

봇이 방금 처리한 요청은 서비스 이벤트다. turns, turn_usage, trace_events, feedback에 row 단위로 남긴다.

Feedback lane

audit row는 나중에 BigQuery로 올라가 bot_quality_daily, bot_cost_daily, bot_feedback_summary 같은 mart가 된다.

설계 포인트

audit_id가 여러 테이블을 묶는 키다. Slack에는 답을 간결하게 남기고, 재현에 필요한 실행 증거는 audit 테이블에 남긴다.

설계를 섞을 때 자주 보이는 증상

구조증상
운영 DB를 BI가 계속 scan서비스 요청과 분석 쿼리가 같은 자원을 사용.
warehouse를 primary app DB처럼 사용짧은 트랜잭션, 상태 업데이트, key lookup 기대치와 어긋남.
Slack 답변에 모든 trace 노출사용자는 읽기 어렵고, 운영자는 구조화된 재현 정보를 잃음.
API가 매 요청마다 BigQuery scan분석에는 빠른 1초도 서비스 응답에는 길 수 있음.

Warehouse

OLTP 기록, event log, SaaS/API 데이터가 warehouse에서 만난다.

RDS CDC
DB에 commit된 row 변화 복제

users, orders, turns처럼 운영 DB의 상태 변화를 transaction log에서 읽음.

Event Log
앱이 직접 발행한 도메인 사건

impression, click, search, prediction request처럼 append-only stream으로 남기는 행동 기록.

Batch Extract
DB, SaaS API, file을 일정 주기로 적재

freshness가 덜 빡빡한 광고비, CRM, 결제, CS, 외부 API 데이터에 자주 사용.

warehouse에는 제품 로그만 모이지 않음

Mart

Feature / Label

ML 학습, 평가, 추천 후보 생성에 재사용.

챗봇 품질 mart 예시

select
  date(started_at) as activity_date,
  status,
  count(*) as turns,
  avg(duration_ms) / 1000 as avg_seconds
from analyst_audit.turns
group by 1, 2;

마케팅 join 예시

select
  campaign,
  sum(ad_spend) as spend,
  count(distinct user_id) as retained_users
from mart_acquisition_daily
group by 1;
구분 포인트

CDC는 DB 상태 변화 복제, event log는 제품 행동 기록. 둘 다 warehouse로 오지만 event time, idempotency key, delete/update 처리 방식이 다르다.

Scheduler

batch는 시간표와 의존성, 재시도, backfill까지 운영한다.

Raw ingest
원천 데이터 도착, partition 준비 상태 확인.
→clean
Staging
타입, key, timezone, dedupe 처리.
→build
dbt build / test
fact, mart, test, docs를 같은 계약으로 실행.
→notify
Dashboard / Slack
Metabase, Slack alert, bot이 새 mart를 소비.
Schedule
언제 실행할지

매일 07:00 KST, 매시간, 특정 데이터 도착 후 실행.

Dependency
어떤 순서로 실행할지

raw 적재 후 staging, staging 후 dbt test, test 후 mart publish.

Retry / Backfill
실패와 과거 재계산

일시 오류 재시도, 누락 partition 재계산, 로직 수정 후 과거 구간 재실행.

Guardrail
freshness, 비용, 알림

데이터 준비 시각, 동시성, pool, 비용 상한, 실패 알림 관리.

Docker / headless

노트북에서 한 번 도는 코드와 계속 켜져 있는 서비스는 운영 조건이 다르다. Docker Compose는 Slack bot, Airflow, Metabase, API를 같은 실행 계약으로 묶고, volume은 state와 log를 보존한다. env는 credential과 endpoint를 주입한다.

수업 메모

실제 계산은 BigQuery, dbt, Python job, API client, worker가 수행한다. scheduler는 실행 시점, 순서, 상태, 재시도, 알림을 관리한다.

ML Serving

offline에서 만든 feature가 online 응답 시간과 만나는 구간.

Offline

긴 기간 로그, label, feature, 모델 학습.
Nearline
minutes freshness
최근 행동을 feature와 후보에 반영.
Online
ms lookup
RDB, Redis, FAISS, online feature store.
Feedback
event log
노출, 클릭, 전환, 오류가 다음 학습 데이터가 됨.
OLAP 분석

BigQuery/StarRocks에서 과거 활동, repo profile, user profile 집계.

Feature / 후보

batch job이 feature table과 사용자별 top-K 후보 생성.

MLflow

split, feature cache, model config, metric, artifact 기록.

Publish

RDB, Redis, FAISS index, API bundle, online store로 배포.

Service feedback

API 응답 후 노출, 클릭, 전환 로그를 다시 적재.

Offline feature store

학습과 backtest용

  • 긴 기간의 feature history 보관.
  • label, split, point-in-time join 관리.
  • 재현 가능한 학습 데이터 생성.

Online feature store

사용자 요청 path용

  • user_id, item_id 같은 key로 낮은 지연 조회.
  • API latency와 cache hit를 같이 관리.
  • offline feature 정의와 freshness 계약을 맞춤.

latency 감각

StarRocks와 BigQuery의 1초 안팎 분석 응답은 분석가에게 충분히 빠른 편이다. 사용자 요청마다 추천 후보를 보여주는 API path에서는 수십 ms 단위의 lookup 계약을 따로 잡는다.

30초 답변

서비스에서 생기는 질문, 답변, 피드백은 row 단위 운영 기록으로 남김. 여러 기록을 모아 추세와 품질을 볼 때는 warehouse와 mart를 읽음. ML 서비스에서는 학습과 feature 집계는 offline에서 만들고, API 요청 path에는 RDB, cache, online feature store를 둠.

질문 1
이 데이터는 방금 발생한 서비스 이벤트인가?

그렇다면 OLTP, audit, event log 쪽에서 시작.

질문 2
많은 기간과 segment를 묶어 봐야 하나?

그렇다면 OLAP, warehouse, mart 쪽으로 이동.

질문 3
매일 같은 순서로 반복되어야 하나?

그렇다면 Airflow 같은 scheduler와 운영 가드레일 필요.

질문 4
사용자가 기다리는 API path인가?

그렇다면 serving store, cache, index lookup 계약을 잡음.
