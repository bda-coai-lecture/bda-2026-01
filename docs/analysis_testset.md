# 분석 워크플로우 테스트셋

`.claude/skills/analysis`가 실제로 작동하는지 채점하는 문제집이다.
문제마다 **정답 숫자가 아니라 "함정을 밟았는가"로 채점한다.** 숫자는 데이터가 갱신되면 바뀌지만 함정은 그대로다.

모든 실측값은 **2026-07-26에 `bda-coai` 실데이터로 직접 검증**했다. 채점 기준선으로 쓴다.

## 채점 방법

| 등급 | 조건 |
|---|---|
| FAIL | 함정 중 하나라도 밟고 그걸 알아채지 못함 |
| PASS | 함정을 전부 피했고 인풋 8종·건강성 표·재현 SQL을 남김 |
| STRONG | PASS + 질문 자체의 결함(정의 모호, 계측 공백)을 먼저 지적함 |

공통 실격 사유(모든 문제에 적용):
- `githubarchive.day.20*`를 `_TABLE_SUFFIX` 없이 조회
- dry run 없이 raw 조회 실행
- 대조군 없이 인과 단정
- 숫자에 기간·분모·분자·grain 미표기
- actor를 "사용자"라고 무비판적으로 지칭

## T1. Event type별 활동 패턴

> Pull Request를 많이 생성하는 사용자와 Push를 많이 하는 사용자의 활동 패턴은 다른가?

**모드** 세그먼트 비교
**소스** `fact_user_repo_activity` (7일 이내 슬라이스)

**실측 (2026-07-01~07-07, actor 단위)**

| 세그먼트 | actor 수 | 평균 활동일 | 평균 repo | 평균 event |
|---|---|---|---|---|
| push_only | 1,817,678 | 1.97 | 1.63 | 11.26 |
| both | 48,394 | 4.04 | 16.79 | 129.66 |
| pr_only | **4,281** | 1.61 | 1.44 | 5.74 |
| neither | 320,783 | 1.08 | 1.23 | 1.75 |

**반드시 잡아야 할 함정**

1. **질문의 전제가 거의 붕괴한다.** "PR을 많이 하는 사용자"에 해당하는 pr_only는 4,281명, 전체의 0.2%다. 실제 대비는 `push_only` vs `both`다. 이걸 지적하지 않고 pr_only 통계를 대표값처럼 쓰면 FAIL.
2. **정의적 순환.** `both`는 정의상 event type이 2종 이상이어야 하므로 event 수가 많을 수밖에 없다. "both가 더 활발하다"는 발견이 아니라 동어반복이다.
3. **"PR을 생성"은 측정 불가.** fact에는 `payload`가 없어 `PullRequestEvent`의 open/close/reopen을 구분할 수 없다. 계측 공백으로 명시해야 한다.
4. **`both`의 평균 16.79 repo는 자동화 오염 의심.** T5의 자동화 비중과 교차 확인해야 한다.
5. 무작위 배정이 아니므로 "PR을 쓰면 활발해진다"류 인과 금지.

**PASS 조건** 1·3을 먼저 말하고, 2를 피하도록 세그먼트 배정 기간과 측정 기간을 분리하거나 최소한 순환을 명시.

## T2. 신규 사용자 유지율 ★핵심 문제

> 처음 활동한 사용자는 일주일 또는 한 달 후에도 계속 활동하는가?

**모드** 리텐션/코호트
**정답 소스** `metrics_retention_weekly` (최초 관측 코호트)

**실측 — 같은 주(2026-03-02), 같은 "W1 리텐션"이라는 이름, 다른 답**

| 모델 | 분모 | W1 |
|---|---|---|
| `metrics_retention_weekly` (최초 관측) | 520,770 | **23.8%** |
| `metrics_cohort_retention_weekly_heatmap` (활동주 롤링) | 2,625,588 | **45.6%** |

**답이 2배 차이 난다. 분모는 5배 차이 난다.**

**실측 — 좌측 절단 (`metrics_retention_weekly` 초반 주차)**

| cohort_week | cohort_users | W1 |
|---|---|---|
| 2025-09-01 | **2,386,312** | 43.4% |
| 2025-09-08 | 1,376,831 | 30.2% |
| 2025-09-15 | 1,160,491 | 26.5% |
| 2025-09-22 | 1,001,688 | 23.6% |

첫 주 코호트가 다음 주의 1.7배다. 이건 신규 유입 급증이 아니라 **관측 시작 시점에 기존 actor가 전부 "최초 관측"으로 잡힌 것**이다. W1도 43.4%로 부풀어 있다.

**반드시 잡아야 할 함정**

1. **모델 선택.** `cohort`라는 단어가 들어간 mart를 아무거나 집으면 답이 2배 틀린다. SQL을 열어 `min(week_start)` 여부를 확인해야 한다.
2. **`metrics_user_retention_weekly`는 함정 이름.** `select *` from `metrics_user_lifecycle_weekly`일 뿐이고, 코호트 리텐션이 아니라 직전 기간 라이프사이클이다.
3. **좌측 절단.** 최소 첫 4주 코호트를 신규 코호트로 쓰면 FAIL.
4. **우측 절단.** "한 달 후"(W4)를 보려면 코호트 시작 후 5주가 지나야 한다. 최근 코호트를 완전 관측 코호트와 같은 표에 넣으면 FAIL.
5. W0는 정의상 100%다. 성과로 보고하면 FAIL.

**PASS 조건** `metrics_retention_weekly`를 고른 이유를 SQL 근거로 대고, 좌·우측 절단 구간을 명시적으로 제외.

## T3. 요일·시간대별 차이 ★핵심 문제

> 요일이나 시간대에 따라 커밋 수(유저 수)가 차이가 있을까?

**모드** 활동량 + 계측 공백 판정 (2단 분해 필요)

**실측 — 요일별 (`metrics_daily`, 2026-01-01~2026-07-18)**

| 요일 | 평균 actor | 평균 event |
|---|---|---|
| Mon | 680,106 | 3,658,023 |
| Tue | 700,342 | 3,637,902 |
| Wed | 693,580 | 3,654,265 |
| Thu | 665,978 | 3,584,382 |
| Fri | 646,494 | 3,652,924 |
| Sat | **565,709** | **3,727,745** |
| Sun | **576,332** | **3,703,044** |

**actor 수와 event 수가 정반대로 움직인다.**
주말 actor는 평일 대비 약 15~19% 적은데, 주말 event는 오히려 **더 많다**.
"요일에 따라 차이가 있나"에 대해 **측정 대상을 무엇으로 잡느냐에 따라 결론이 뒤집힌다.**

유력한 설명은 T5의 자동화 actor다. 사람은 주말에 쉬지만 봇은 쉬지 않는다.
검증하려면 `dim_push_automation_actor`를 제외하고 다시 계산해야 한다.

**실측 — 시간대는 계측 공백, 그러나 싸다**

| 필요한 것 | fact | raw 1일 dry run |
|---|---|---|
| 시각(hour) | 없음 (`activity_date`만) | `created_at`, PushEvent 1일 = **74,451,736 B (71 MB, 약 $0.0004)** |
| 커밋 수 | 없음 (event 수만) | `payload`의 `$.size`/`$.distinct_size`, PushEvent 1일 = **1,079,187,147 B (1.03 GB, 약 $0.0063)** |

**반드시 잡아야 할 함정**

1. **"커밋 수 ≠ event_count".** PushEvent 1건에 커밋이 여러 개다. `total_events`를 커밋 수라고 부르면 FAIL.
2. **actor와 event의 결론 역전을 놓치면 FAIL.** 하나만 보고 "주말에 줄어든다" 또는 "차이 없다"라고 답하면 둘 다 틀렸다.
3. **시간대를 "데이터가 없다"로 끝내면 감점.** `fact에는 없음 / raw 1일 71 MB면 가능`까지 가야 STRONG이다.
4. UTC 기준이다. "새벽에 활동이 많다"는 해석은 시간대 정의를 밝히기 전엔 무의미하다.
5. 질문이 `커밋 수(유저 수)`로 두 지표를 괄호로 묶어 뭉갰다. 이 모호함을 먼저 지적하면 STRONG.

**PASS 조건** 요일은 답하고, 시간대는 견적과 함께 승인 요청하고, 지표 역전을 명시.

## T4. 기여자 집중도와 휴면

> 상위 1~2명의 기여자가 전체 커밋의 80% 이상을 차지하는 프로젝트는 시간이 지나면서 휴면 상태가 될 확률이 높을까?

**모드** 라이프사이클 단계
**소스** `fct_push_repo_episode` + fact 조인 필요

**실측 (`fct_push_repo_episode` 전체)**

| 항목 | 값 |
|---|---|
| as-of (`data_through_date`) | **2026-07-18** |
| 최소 episode_start_date | 2025-05-29 (= 2025-05-01 + 28일, 좌측 절단 방어) |
| 에피소드 수 | 81,211,316 |
| provisional (이탈 판정 불가) | 7,839,826 (**9.65%**) |
| 생애 기여자 1명뿐 | 75,942,743 (**93.51%**) |

**반드시 잡아야 할 함정**

1. **질문의 전제가 93.5%에서 무너진다.** 에피소드의 93.5%는 생애 기여자가 **1명**이다. 그런 repo는 정의상 상위 1명이 100%를 차지한다. 임계값 80%는 거의 모든 repo를 통과시켜 변별력이 없다. 다중 기여자 에피소드로 한정해야 질문이 성립한다.
2. **`normalized_entropy`는 기여자 집중도가 아니다.** 모델 SQL을 보면 **주별 push 분포**의 Shannon 엔트로피다. 시간적 집중도지 사람 집중도가 아니다. 이걸 기여자 집중도로 쓰면 FAIL.
3. **기여자 점유율은 mart에 없다.** `entry_actor_count`/`lifetime_actor_count`는 인원 수일 뿐 점유율이 아니다. 에피소드 × actor별 push 합계를 fact에서 다시 만들어야 한다.
4. **"커밋" ≠ push event.** T3과 동일.
5. **as-of 미표기.** 이탈률은 2026-07-18 기준이다. fact는 2026-07-25까지 있으므로 **에피소드 mart가 7일 뒤처져 있다.** 이걸 안 적으면 FAIL.
6. **provisional 9.65%를 분모에 넣으면 이탈률이 과소 추정된다.**
7. **자동화 actor 미제외** (T5 참조). 봇이 기여자 수를 부풀린다.

**PASS 조건** 1과 2를 먼저 지적하고, 3의 재구성 비용을 견적으로 제시.

## T5. 자동화 제외 후 에피소드 재분절 (파이프라인 과제)

> 1. 완료된 UTC shard만 읽어 자동화 actor(`dim_push_automation_actor`) 기준을 갱신한다.
> 2. 자동화 계정을 제외한 순수 push actor-day 및 repo-day를 생성한다.
> 3. repo 및 actor 에피소드를 28일 규칙에 맞춰 처음부터 다시 분절 계산한다.
> 4. 1일 또는 7일 소규모 범위에서 grain 중복, null, 합계 보존을 검증한다.
> 5. 검증된 모델만 빌드하고, 리포트에 고정 관찰창과 as-of 날짜를 명시한다.

**모드** 데이터 품질 진단 → 승격

**실측 — 왜 이 과제가 필요한가 (2026-07-01~07-07, PushEvent)**

| 항목 | 값 |
|---|---|
| 전체 push actor | 1,866,072 |
| 자동화 actor | 5,000 (**0.27%**) |
| 전체 push event | 23,781,846 |
| 자동화 event | 3,790,747 (**15.94%**) |

**actor의 0.27%가 event의 15.94%를 만든다.**
actor 기준 지표는 거의 안 흔들리고 event 기준 지표는 6분의 1이 날아간다. 둘을 나눠 보고해야 한다.

**확인된 현재 갭**
- `fct_push_repo_episode`는 `fact_user_repo_activity`에서 `action='PushEvent'`를 바로 읽는다. **자동화 actor를 제외하지 않는다.**
- **actor 단위 에피소드 모델이 아예 없다.** repo 단위만 있다. 3번은 신규 개발이다.
- `dim_push_automation_actor`는 `analysis_start_date`~`analysis_end_date` 범위의 raw를 스캔한다. 1번의 "완료된 shard만"은 `analysis_end_date`를 최신 완료 UTC 일자로 넘기라는 뜻이다.

**반드시 잡아야 할 함정**
1. `dim_push_automation_actor` 갱신은 raw 스캔이다. **범위와 dry run 없이 돌리면 FAIL.**
2. 자동화 제외는 `explicit_bot`만이 아니라 `machine_rate_suspect`도 있다. 어느 기준을 쓸지 선택하고 근거를 남겨야 한다.
3. 에피소드 재분절 시 좌측 절단 방어(`>= source_start + 28일`)를 유지해야 한다. 빼먹으면 앞부분 에피소드가 가짜로 생긴다.
4. 합계 보존 검증은 raw `count(*)` vs fact `sum(event_count)`다. fact row count와 비교하면 FAIL.
5. 전체 backfill을 승인 없이 돌리면 FAIL. 선택 빌드만.
6. 5번의 "고정 관찰창"은 우측 절단 통제다. `metrics_push_repo_episode_started_30d_monthly`가 이미 쓰는 패턴이니 재발명하지 말 것.

**PASS 조건** 5단계를 순서대로 수행하되 각 단계 앞에 dry run 견적을 붙이고, 3번이 신규 모델 개발임을 인지.

## 기본 문제 (워밍업)

### B1. 활동량 — mart 커버리지 경계

> 2025년 6월 GitHub 활동량 추이를 보여줘.

**함정** `metrics_daily`는 **2025-09-01부터만 존재한다.** 2025-06-15를 조회하면 **0행**이 나온다.
그런데 같은 날짜에 `fact_user_repo_activity`와 `stg_user_repo_activity`에는 **1,148,747행 / 3,472,378 event**가 있다.

| 소스 | 커버리지 |
|---|---|
| `fact_user_repo_activity` | 2025-05-01 ~ 2026-07-25 (일자 누락 없음) |
| `stg_user_repo_activity` (view) | 동일 |
| `metrics_daily` / `metrics_weekly` / `metrics_retention_weekly` | **2025-09-01 ~** |
| `metrics_cohort_retention_weekly_heatmap` | 2025-04-28 ~ |

**FAIL** "2025년 6월은 데이터가 없습니다"라고 답함.
**PASS** mart와 fact의 커버리지가 다르다는 것을 발견하고, fact로 내려가 답하며, 답변에 mart 커버리지 경계를 명시.

**이건 버그가 아니라 백필 경계다.** 플랫폼 운영을 시작한 지 얼마 안 됐고 fact만 2025-05-01까지
앞으로 채워둔 상태다. mart는 그 백필을 따라가지 않았을 뿐이다.

그래서 더 좋은 문제다. 고장이 아니라 **정상 운영 중에도 상시 존재하는 상태**이므로,
"mart가 0행이면 데이터가 없는 것"이라는 추론은 앞으로도 계속 틀린다.
mart 커버리지는 지표가 아니라 **적재 이력의 함수**라는 걸 체득하는 게 이 문제의 목적이다.
2026-07-26 확인.

### B2. 데이터 품질 진단 — raw ↔ fact 정합

> 2026-07-01 하루치가 raw와 mart에서 일치하는지 확인해줘.

**함정**
- raw `count(*)`를 fact **row count**와 비교 → FAIL. 비교 대상은 `sum(event_count)`.
- `_TABLE_SUFFIX` 없이 raw 조회 → 즉시 FAIL.
- fact는 최근 3일 replace-days로 적재된다. 그보다 오래된 지연 도착은 반영되지 않는다.

### B3. 계측 공백 판정

> 어떤 프로그래밍 언어가 가장 활발한지 알려줘.

**함정** GitHub Archive 이벤트에는 언어 정보가 없다. fact에도 raw에도 없다.
`data/repo_metadata.db`(GitHub REST API 캐시)에 일부 있지만 전수가 아니고 수집 시점이 다르다.

**FAIL** repo 이름이나 event type으로 언어를 추정.
**PASS** raw에도 없음을 명시하고, 메타데이터 캐시의 커버리지 한계를 정량화한 뒤, 무엇을 수집해야 답할 수 있는지 제시.
