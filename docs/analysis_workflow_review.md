# 외부 분석 워크플로우 리뷰 — bda-2 적용 판정

받아온 문서: "햄찌식 오픈 데이터셋 분석 워크플로우" (사내 구조를 지운 오픈 데이터셋 연습용 가이드).
이 문서는 그 가이드를 bda-2 환경(GitHub Archive → BigQuery → dbt mart → Metabase)에 옮길 때
**무엇이 그대로 살고, 무엇이 깨지고, 무엇을 새로 붙여야 하는지**를 판정한 기록이다.

판정 기준은 하나다. 우리 데이터로 **검증 가능한가**.

## 0. 한 줄 결론

원문의 **절차 골격(모드 분류 → 인풋 고정 → 구조 매핑 → 건강성 검증 → 분석 → 기록)은 그대로 쓴다.**
다만 원문은 "구조를 모르는 데이터셋을 처음 열어본다"를 전제하는데 우리는 정반대다.
우리는 **구조를 이미 dbt로 소유하고 있고, 대신 원천이 크고 과금된다.**
그래서 세 가지를 바꿔야 한다.

1. "데이터 구조 매핑" 단계 → **"기존 lineage에서 가장 싼 신뢰 가능 소스 찾기"** 로 교체
2. "가드레일 지표" → 에러율/환불률이 아니라 **스캔 바이트와 shard 완결성**
3. "결측/중복" 중심의 건강성 검증 → **좌·우측 절단(censoring)과 자동화 actor 혼입** 중심으로 교체

## 3. 우리 환경에서 깨지는 것

### 3.1 AB 테스트 모드 (원문 5.4) — **적용 불가**

GitHub Archive는 공개 이벤트 로그다. 우리는 실험 주체가 아니고, variant 배정 테이블도 노출 로그도 없다.
원문이 "데이터에 기록된 배정값을 읽어라"라고 한 그 배정값 자체가 존재하지 않는다.

- 판정: **모드에서 삭제.** 흉내 내면 반드시 해시로 임의 배정하게 되고, 원문이 금지한 바로 그 짓이 된다.
- 대체: `준실험/세그먼트 비교` 모드. 대조군은 만들 수 없고 **비교군만** 만들 수 있다는 것을 이름에서부터 못박는다.

### 3.2 퍼널 모드 (원문 5.2) — **대부분 계측 공백**

원문의 퍼널은 `노출 → 클릭 → 입력 → 제출 → 성공`이다. 우리 fact는 `payload`를 버리고
`type`만 남기므로 제품 퍼널 단계가 아예 없다. PR이 열렸는지 머지됐는지도 fact에서는 알 수 없다.

- 판정: **제품 퍼널은 불가.** 대신 우리가 실제로 가진 단계형 구조는 라이프사이클이다.
  - repo: 첫 Push → 진입주 협업 여부(`entry_actor_count`) → 28일 생존/이탈(`fct_push_repo_episode`)
  - actor: 첫 활동주 → W1 재활동 → W4 재활동 (`metrics_retention_weekly`)
- 이름을 `퍼널`이 아니라 **`라이프사이클 단계 분석`** 으로 바꾼다. 퍼널이라 부르면 전환율처럼 해석된다.

### 3.3 "결측/중복이 조금 있으면 좋다" (원문 0. 준비물) — **전제가 반대**

우리 fact는 `user_id`, `repo_id`, `action`, `event_count`, `activity_date` 전부 dbt `not_null` 테스트가 걸려 있고
staging에서 한 번 더 걸러진다. null을 찾는 검증은 거의 항상 PASS로 통과하고, 통과했다는 사실이 안전감만 준다.

우리의 실제 위험은 네 가지고, 원문에는 셋이 없다.

| 위험 | 설명 | 원문에 있나 |
|---|---|---|
| 우측 절단 | 28일 이탈 규칙, 12주 코호트가 최근 구간에서 미완성 | 부분적 ("부분 관측 코호트") |
| 좌측 절단 | 2025-05-01 이전 이력이 없어 그 시점 기존 유저가 전부 "신규"로 보임 | **없음** |
| 자동화 actor 혼입 | `[bot]` 로그인, 분당 100+ push. `dim_push_automation_actor`로 식별은 하지만 **기본 mart는 제외하지 않는다** | **없음** |
| shard 미마감 | 최신 UTC 일자가 아직 닫히지 않았거나 지연 도착 | 부분적 ("최신성") |

- 판정: 건강성 검증표를 **절단·혼입 중심으로 재작성.**

### 3.4 가드레일 지표 (원문 2. 인풋 7종) — **정의 교체**

원문의 가드레일은 에러율·환불률·취소율이다. 우리에겐 그런 게 없다.
우리 가드레일은 분석 행위 자체가 유발하는 비용과 신뢰도다.

- 교체: **스캔 예산(dry-run bytes)** + **as-of / 관찰창 고정**
- 인풋을 7종 → **8종**으로 늘린다. 8번이 스캔 예산이다.

### 3.5 "데이터셋을 받으면 구조를 읽는다" (원문 3) — **순서 교체**

원문은 테이블 역할을 처음부터 분류하라고 한다. 우리가 매번 그러면 raw로 직행하게 되고 그게 제일 비싼 실수다.
우리는 구조를 이미 안다. 필요한 건 발견이 아니라 **선택**이다.

- 교체: `dbt ls`로 lineage를 먼저 검색 → `marts → staging/fact → 제한된 raw` 순으로 내려간다.
- raw까지 내려가야 하면 그건 곧 **계측 공백을 fact가 못 덮는다**는 뜻이므로, 리포트에 그 사실을 남긴다.

### 3.6 시각화 (원문 6) — **거의 유지, 한 줄 추가**

일별 라인 차트 기본, 차트 제목에 지표·grain·기간을 넣는 규칙은 그대로 좋다.
다만 우리는 Metabase에 이미 카드가 있으므로 **새로 그리기 전에 기존 카드를 확인**하는 단계를 앞에 붙인다.

## 4. 새로 붙여야 하는 것 (원문에 없음)

### 4.1 mart 정의 충돌 확인

이름이 비슷한데 정의가 다른 mart가 이미 공존한다. 이건 실제로 밟은 지뢰다.

| 모델 | cohort 기준 | 실제 의미 |
|---|---|---|
| `metrics_retention_weekly` | `min(week_start)` per user | **최초 관측 코호트.** "신규 유저 리텐션"이 맞음 |
| `metrics_cohort_retention_weekly_heatmap` | 유저가 활동한 **모든** 주 | **활동주 롤링 코호트.** 신규 유저가 아님 |

"신규 사용자 유지율"을 물었을 때 후자를 집으면 조용히 틀린다. 두 모델 다 `cohort`라는 단어를 쓰고, 둘 다 존재하고, 둘 다 값이 나온다.

- 규칙: **지표 이름이 겹치는 모델이 둘 이상이면 SQL을 열어 정의를 확인하기 전에는 숫자를 인용하지 않는다.**

### 4.2 actor 의미론 고정

`user_id`는 `actor.id`다. 사람도 아니고 조직도 아니다. 봇 계정도 actor다.
A가 조직 B 아래에서 이벤트를 일으키면 활성 actor는 A이고 B는 세지 않는다.

- 규칙: 결론에 "사용자"라고 쓰기 전에 **actor / 사람 / 조직** 중 무엇인지 정한다.

### 4.3 자동화 actor 제외 정책을 인풋으로 승격

`dim_push_automation_actor`가 있는데도 `metrics_daily`, `fct_push_repo_episode`는 이를 제외하지 않는다.
즉 "제외했는지 여부"가 모델마다 다르다. 그러면 이건 분석마다 선택해야 하는 **입력**이다.

- 규칙: 인풋 표의 `제외 조건`에 `automation_actor: 제외/포함`을 명시적으로 적는다. 비워둘 수 없다.

### 4.4 as-of 날짜와 고정 관찰창

`fct_push_repo_episode`는 `data_through_date`, `is_provisional`, `is_churn_observable`을 이미 내보낸다.
원문에는 이 개념이 없다. 같은 쿼리를 일주일 뒤에 돌리면 "이탈률"이 바뀐다.

- 규칙: 리포트에 **as-of 날짜와 관찰창 길이**를 반드시 적는다. 적지 않은 이탈률/생존율은 무효로 본다.

## 5. 최종 모드 매핑

원문 6개 모드 → 우리 6개 모드.

| 원문 모드 | 우리 모드 | 판정 | 주 소스 |
|---|---|---|---|
| 사용량 분석 | 활동량 분석 | 그대로 | `metrics_daily`, `metrics_event_type_daily` |
| 퍼널 분석 | 라이프사이클 단계 분석 | **개명** | `fct_push_repo_episode`, `metrics_retention_weekly` |
| 전후 비교 | 전후 비교 | 그대로 (대조군 없음 경고 강화) | `metrics_daily` + 요일 분해 |
| AB 테스트 분석 | **삭제** → 세그먼트 비교 | **대체** | `metrics_user_segments`, actor 세그먼트 |
| 리텐션/코호트 | 리텐션/코호트 | 그대로 (좌측 절단 경고 추가) | `metrics_retention_weekly` |
| 데이터 품질 진단 | 데이터 품질 진단 | 확장 (raw↔fact reconciliation) | fact vs `githubarchive.day.20*` |
| — | **계측 공백 판정** | **신규** | fact에 없으면 raw 비용 견적부터 |

마지막 모드가 핵심이다. 원문은 "데이터에 없으면 계측 공백이라고 적어라"에서 끝나는데,
우리는 raw로 내려가면 대부분 답이 있다. 대신 돈이 든다.
그래서 "없음"이 아니라 **"fact에는 없음 / raw에서 N GB 스캔하면 가능"** 이 정답이 된다.
