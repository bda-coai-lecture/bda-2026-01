# 질문 접수 양식

Slack에서 들어오는 질문은 대개 분석 계약이 아니다. **추측으로 메우지 말고 이 양식을 먼저 채운다.**

## 표준 지시 4개

어떤 질문이 오든 아래 4개는 항상 적용한다.

1. **스키마를 가정하지 않는다.** 컬럼이 있을 것 같다고 쓰지 말고 `references/data_map.md`에서 확인하거나 모델 SQL을 연다. 이름이 의미를 보장하지 않는다 (`user_id`는 actor다, `event_count`는 커밋 수가 아니다).
2. **대조군이 없으면 인과를 말하지 않는다.**
3. **표본이 작으면 "차이 없음"이 아니라 "판단 불가"라고 말하고**, 무엇을 얼마나 더 봐야 답이 나오는지 적는다.
4. **최종 답변에 사용한 모델·필터·기간·grain을 명시한다.**

## 접수 양식

```markdown
## 접수

| 항목 | 사용자가 말한 것 | 내가 확정한 것 | 상태 |
|---|---|---|---|
| 질문 | | | |
| 이 답으로 내릴 결정 | | | 확인됨/미확인 |
| 기간 | | | 확인됨/추론 |
| 분석 단위(grain) | | | 확인됨/추론 |
| 제외 조건 | | automation_actor: | 확인됨 |
| 핵심 지표 1개 | | | 확인됨/추론 |
```

`내가 확정한 것`이 `사용자가 말한 것`과 다르면 **그 차이를 답변 첫 줄에 밝힌다.**

## 되물어야 하는 경우

아래 중 하나라도 해당하면 바로 쿼리하지 말고 한 문장으로 되묻는다.

| 신호 | 되물을 것 |
|---|---|
| 지표 이름이 우리 mart에 둘 이상 존재 | "리텐션은 최초 관측 코호트 기준인가요, 직전 기간 기준인가요?" |
| 기간이 없음 | "기간을 언제로 잡을까요? 기본값은 최근 완료된 4주입니다" |
| "사용자"라고 했는데 actor/사람/조직이 갈림 | "actor 기준으로 세면 봇이 포함됩니다. 그대로 갈까요?" |
| raw 스캔이 필요하고 견적이 예산을 넘음 | "fact에는 없고 raw에서 N GB 스캔하면 가능합니다. 진행할까요?" |

**되묻는 것은 한 번만 한다.** 답이 없거나 애매하면 가정을 명시하고 진행한다.
아무것도 못 하고 멈추는 것이 가장 나쁜 결과다.

## 질문 재작성

모드가 모호하면 분석 가능한 형태로 다시 쓰고, 주의 한 줄을 붙인다.

```text
원래: 최근에 활동이 줄었나?
분석 가능: 2026-06-01~2026-07-25 일별 active actor 수가 직전 동일 길이 구간 대비 어떻게 변했나?
주의: 대조군이 없으므로 관측된 변화로만 해석한다. 2026-07-25는 shard 마감 여부를 먼저 확인한다.
```

```text
원래: 요일이나 시간대에 따라 커밋 수(유저 수)가 차이가 있을까?
분석 가능: (a) 요일별 push actor 수와 push event 수가 각각 어떻게 다른가?
          (b) 시간대는 fact에 없다 — raw 스캔 견적을 먼저 낸다.
주의: 질문이 "커밋 수"와 "유저 수"를 묶었는데 둘은 다른 지표이고 실제로 반대로 움직인다.
     "커밋 수"는 event_count가 아니다.
```

## 계측 공백일 때의 답변 형식

**"데이터가 없습니다"로 끝내지 않는다.**

```text
fact에는 없습니다. githubarchive.day의 payload에서 뽑을 수 있습니다.
2026-07-01 하루, type='PushEvent'로 좁히면 dry run 기준 1.03 GB (약 $0.006)입니다.
진행할까요?
```
